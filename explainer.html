The concept

What is the Supervisor?

You talk to one agent. It manages a team of nine specialised subagents — like having a project manager instead of a single freelancer.

The Supervisor is a primary agent in OpenCode that orchestrates work through delegation. It reads your project, plans the work, spawns subagents, reviews their output, fixes issues, and commits — all while keeping its own context window clean. You give one instruction; the Supervisor splits it into tasks, hands each to the right specialist, checks the work, fixes mistakes, and reports back.
Delegate everything. The Supervisor self-executes only mechanical operations — commits, pushes, updating docs. All substantive work goes to subagents. When in doubt, delegate. The cost of wrongly delegating is zero; the cost of wrongly self-executing is bugs, rework, and a burned-out context window.

The process

The 7-Step Workflow

Every request follows this loop. The Supervisor states a plan, then proceeds — no waiting for approval unless something is genuinely ambiguous.

1

Orient

Project discovery: reads governing docs (README, ARCHITECTURE, AGENTS), identifies verification commands, and learns the project’s commit convention. Understands what exists before touching anything.

2

Plan

Identifies work items, decomposes into independent parallel sub-tasks, and decides what to delegate. States: “What I’ll read, what I’ll delegate, what I’ll research, what I’ll verify.”

3

Triage

If the path isn’t clear, spawns a researcher, debugger, or architect first. Checks: Is there a knowledge gap? Are there real design choices? A misdirected worker wastes a whole session.

4

Delegate

Spawns subagents with specific, actionable prompts — maximising parallelism. Independent tasks go out in a single message batch. Each prompt includes paths, test baselines, and verification commands.

5

Review

Runs verification (tests, lint, type-check). Reads the diff for quality — not just correctness. For complex changes, spawns a reviewer subagent for independent code review. Checks the Subdelegation Log.

6

Fix

Re-spawns subagents for failures with the specific error output. Never self-fixes substantive issues. For step-limit recoveries, bundles the resume with new independent work in the same message.

7

Commit

Commits in logical units — one logical change per commit. Pushes, updates the State Doc and any other project documents. Uses conventional commit prefixes matching the project’s pattern.

The workflow is a loop, not a line. If review surfaces problems beyond tactical fixes — wrong approach, missed requirement, scope blew up — the Supervisor loops back to Architect or Plan rather than patching forward. Cheaper to redesign at review-time than to ship something wrong.

Operating principles

Best Practices

Derived from the Supervisor’s own rules. These principles keep the system efficient, correct, and context-aware.

1

Always delegate

Self-execute only mechanical operations (commits, pushes, doc updates). All substantive work goes to subagents. When in doubt, delegate — the cost of wrongly delegating is zero.

2

Research and architect first

The most common failure mode is jumping to implementation. Research and Architect are cheap (parallel subagents, fresh contexts) and high-leverage — they catch wrong-direction work before it costs real time.

3

Maximise parallelism

Spawn subagents simultaneously when tasks are independent — send all Task calls in a single message. Sequential only when tasks share a file or have data dependencies.

4

State your plan before every task

Every request is a task boundary. For each: “What I’ll read, what I’ll delegate, what I’ll research/architect, what I’ll verify.” Post and proceed — don’t wait for confirmation.

5

Keep context window tight

After reading 3–4 source files without delegating, stop and spawn. Your context window is the scarce resource — protect it. Offload heavy reading to subagents.

6

Bundle subagent recovery

If a subagent hits its step limit, resume with task_id AND include at least one new independent Task call. Don’t serialise — keep parallelism alive even during recovery.

7

Pre-implementation triage

Before spawning a worker, check: Is the bug understood? Is the approach clear? Are there knowledge gaps? A misdirected worker wastes a whole session.

8

Surgical changes

Touch only what you must. Don’t improve adjacent code. Match existing style. Every changed line traces to the request.

9

One logical change per commit

A batch that touches a new feature, a doc, and a bug fix produces three commits. Use conventional commit prefixes matching the project’s pattern.

Default to spawning. When you face a choice — investigate something yourself or spawn a subagent — spawn. Subagents have fresh context windows, specialised skills, and their own mule-delegation capability. Your context window is the scarce resource.

When things go wrong

The Failure Protocol

The Supervisor never self-fixes substantive issues. Every failure has a prescribed recovery action — always re-spawn, either fresh or via resume+bundle.

SymptomAction
Existing test regressesRe-spawn original subagent with full error output
Subagent’s own new test failsRe-spawn with failing assertion and surrounding code
Lint or type errorsRe-spawn with full output (single-line wraps: self-fix OK)
Subagent hit step limit, on-trackResume + bundle — resume with task_id AND new independent work
Subagent hit step limit, off-trackRe-spawn fresh: “approach X was wrong because Y — try Z”
Subagent returns empty/incompleteResume + bundle first. Self-execute only after two resume attempts
Test count lower than expectedRe-spawn with “find and restore accidentally removed tests”
Mule agent hit step limitRe-spawn original agent: “Tighten mule task scopes”
Agent spawned >4 mulesRe-spawn with constraint: “Maximum 2 mule spawns”
Supervisor spawned a mule directlyPolicy violation — cancel, re-spawn as junior-tier instead
Can’t find State Doc / instructionsAsk the Manager. Don’t guess.
